\begin{abstract}
    Sparse linear algebra kernels are foundational to scientific computing, but also notoriously difficult to accelerate. Particular challenges arise due to their irregular memory access and load imbalance. We investigate these challenges on a spatial dataflow architecture: the Cerebras Wafer-Scale Engine (WSE). Designed for dense neural network workloads, this architecture promises extremely low latency memory access but requires the right algorithm and data placement, presenting a difficult design problem for sparse workloads.

    The sparse matrix-vector product (SpMV) is a simple but valuable first case study on the WSE.
    We present the first algorithm for SpMV on the WSE and a companion communication model.
    We evaluate both across various matrix sizes and structures, demonstrating the accuracy and utility of the communication model and discussing its shortcomings.
    We also compare the WSE SpMV implementation to a CuSparse equivalent for context to more conventional implementation performance.
    This work provides insight into the utility of spatial dataflow architectures for general sparse workloads and
    informs the most important directions for future work.
\end{abstract}

\section{1D Collectives}
Luczynski et al. originally present a set of 1D and 2D collectives implemented in CSL for the Cerebras WSE \cite{Luczynski_2024}. In this work, we focus on the 1D broadcast and reduce where each PE contributes exactly one vector element to each broadcast or reduce. These collectives are described by the first two parameters in \ref{tab:notation}, where $B$ and $P$ represent the same concepts as in the original paper. Note that here we understand $B$ slightly differently. Instead of referring to it as the vector size per PE, we understand $B$ as the number of consecutive vectors that are operated on. In this sense, it can be interpreted as the number of pipelined iterations of broadcast or reduction.

In the original presentation of these collectives, Luczynski et al. also develop a performance model for them. This performance model is based on the parameters $P$ and $B$ and an additional variable $T_r$, the ramp latency. Specifically, $T_r$ captures the latency between message arrive on a PE at the router to that message being received by the compute engine.

We build on Luczynski et al. by (1) implementing the collectives in Tungsten and Paint, and (2) updating the performance model. Additionally, we introduce a new parameter $S$, the single-hop latency between PEs, from router to router. While this paramter clearly plays in to the results in earlier work, it has not yet been explicitly named. Additionally, we highlight the extra latency between PEs at reticle boundaries, $S_{ret}$, and factor it in to our updated performance modeling in addition to a parameter $C$ which denotes the number of reticle boundaries crossed. In practice, $C$ and depends on both the length of the PE region $P$ and if the collective is vertical (column) or horizontal (row).

Luczynski et al. find the ramp latency $T_{ramp}$ to be around 2 cycles, while an earlier work from Tramm et al. estimates 7 cycles. In evaluation of our collectives, we find $T_r = 5$ and $S = 2$. Results from a pingpong benchmark give us $S_{ret} = 9$.

\section{Two-Phase SpMV}
We implement an algorithm to compute the sparse matrix-vector product  $Ax = y$ on the WSE using the 1D collectives as a basis.
At a high level, the algorithm involves distributing the coefficients of $A$ across a 2D grid of PEs, broadcasting values of $x$ vertically through PE columns, and reducing values of $y$ across PE rows. The algorithm makes some assumptions about the matrix layout but otherwise supports a wide parameter space across various matrix mappings, sparse storage options, and PE grid size choices. In the following discussion, we assume $A$ and the PE grid are both square, using $N$ to refer to the dimension of $A$ and $P$ to refer to the dimension of the PE grid.

\textbf{Matrix Mappings:}
We use the term 'mapping' to refer to how the coefficients of $A$ are placed on the PE grid, within the constraint of RCL. In this work, we explore three mappings: blocked, cyclic, and random. The blocked mapping does a basic 2D blocked decomposition of the rows and columns of $A$. This mapping is perhaps the easiest to visualize, but often produces large load imbalance across PEs, especially when the matrix has some sort of structure. The cyclic and random mappings attempt to address this problem by partitioning rows and columns either cyclically (round-robin fashion) or randomly.

\subsection{Dataflow Algorithm}
Assuming that the matrix $A$ is distributed on the 2D mesh under a mapping that preserves row and column locality, the SpMV can be conceptually
broken down into two simple 1D collective phases:
\begin{enumerate}
    \item Broadcast values of $x$ down mesh columns in the order prescribed by the mapping.
    \item Reduce rows of partial products across mesh rows also in the order prescribed by the mapping.
\end{enumerate}

Ensuring that broadcasts and reductions proceed in a prescribed order means that indices of $x$ and row indices of the reductions do not need to be communicated - instead, they are implied by the order of arrival.
In our implementation, the values of $x$ and the resulting values of $y$ are stored in 'moat' PEs: an extra row of PEs is set aside at the top of the
mesh onto which the initial values of $x$ are loaded. Similarly, an extra column of PEs is allocated to the left of the grid wherein the result values $y$ are stored
once computed. Alternatively, the implementation could be updated to stream the values of $x$ and $y$ on and off the mesh, eliminating the need for moat PEs and the corresponding buffers for $x$ and $y$. This streaming optimization is left for future work.

Locally, each PE processes the SpMV in three distinct phases with serialization points between them.
\begin{enumerate}
    \item Store all incoming broadcasts for the PE column
    \item Complete all local compute for each output row
    \item Contribute all results to row reductions
\end{enumerate}
In theory, local synchronizations between these three components are not necessary. For example, early incoming broadcasts could trigger some subset of the compute before all broadcasts are received.
While Tungsten does provide constructs that would support more overlap
of communication and computation here, we evaluated a couple different approaches and found that the serial approach consistently performed best.

Even though the kernel for each PE enforces this serialization, the global algorithm is not bulk-synchronous. Broadcasts and reductions can proceed
in increments of single PE steps, allowing incremental progress through the grid and an overlap of communication and computation. In practice, this might look like reductions near the top of the grid completing before those lower in the grid. We expect that this wavefront behavior would allow some pipelining of multiple SpMVs but this evaluation is left for future work.

\subsection{PE-Local Storage Format}
We implement two standard matrix storage formats: CSR and COO. These dictate only the storage of each PE's individual domain and are completely independent of the mapping strategies.
The COO algorithm \ref{alg:coo} avoids the nested for loop of the CSR algorithm \ref{alg:csr} and is therefore apparently friendlier to the Tungsten compiler.
On the other hand, COO replaces the $Aptr$ data structure, which has length corresponding to the number of local rows, with
a rowids data structure with an entry for each non-zero, potentially contributing to memory pressure depending on the sparsity structure of the matrix.
In evaluation in Section \ref{sec:coovscsr}, we find that COO is typically much more efficient than CSR.

\begin{algorithm}
    \caption{SpMV Kernel in CSR Format}
    \label{alg:csr}
    \begin{algorithmic}[1]
        \ForAll{$r \in \texttt{rows}$}
        \State $sum \gets 0$
        \For{$nnz \gets \texttt{Aptr}[r]$ \textbf{to} $(\texttt{Aptr}[r+1]-1)$}
        \State $sum \gets sum + \texttt{vals}[nnz] \cdot \texttt{x}[ \texttt{colids}[nnz]]$
        \EndFor
        \State $\texttt{partial}[r] \gets sum$
        \EndFor
    \end{algorithmic}
\end{algorithm}

\begin{algorithm}
    \caption{SpMV Kernel in COO Format}
    \label{alg:coo}
    \begin{algorithmic}[1]
        \ForAll{$n \in \texttt{nnzs}$}
        \State $sum \gets \texttt{vals}[nnz] \cdot \texttt{x} [\texttt{colids}[nnz]]$
        \State $r \gets \texttt{rowids}[nnz]$
        \State $\texttt{partial}[r] \gets \texttt{partial}[r] + sum$

        \EndFor
    \end{algorithmic}
\end{algorithm}

\subsection{WSE Pre-processing}
Once a matrix is chosen, a pre-processing step generates the corresponding input files for the WSE.
This step requires the matrix itself, the size of the PE grid, the mapping strategy (blocked, cyclic, random), and the format (COO, CSR).
The result of pre-processing is a set of binary files describing the data to be loaded on to the device.
This pre-processing step is not measured in algorithm runtime, and would in theory be reusable across multiple iterations of SpMV on the same matrix.

\subsection{CuPy Comparison}

We evaluate using a CuSparse SpMV implementation on a single H200, also in 32-bit float precision.
Specifically, we use the COO configuration $CUSPARSE_SPMV_COO_ALG1$ which has demonstrated the best performance on SuiteSparse matrices in recent literature \cite{gao2024systematicliteraturesurveysparse}.
On our selection, this configuration achieves up to a 1.3x speedup over the default CuPy implementation selection. Each GPU datapoint includes 20 warmup iterations and an average timing over 50 subsequent trials.
