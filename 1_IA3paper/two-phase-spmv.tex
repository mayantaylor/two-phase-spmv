\begin{abstract}
    Sparse linear algebra kernels are foundational to scientific computing, but also notoriously difficult to accelerate. Particular challenges arise due to their irregular memory access and load imbalance. We investigate these challenges on a spatial dataflow architecture: the Cerebras Wafer-Scale Engine (WSE). Designed for dense neural network workloads, this architecture promises extremely low latency memory access but requires the right algorithm and data placement, presenting a difficult design problem for sparse workloads.

    The sparse matrix-vector product (SpMV) is a simple but valuable first case study on the WSE. We present the first algorithm for SpMV on the WSE and a companion performance model that aims to capture algorithmic tradeoffs and enable configuration selection. We evaluate both across various matrix sizes and structures and compare to conventional implementations.

    This work provides insight into the utility of spatial dataflow architectures for general sparse workloads and informs the most important directions for future work.
\end{abstract}

\section{Two-Phase SpMV}
\begin{enumerate}
    \item The 1D collectives can be combined for SpMV.
    \item Distribute matrix nonzeros on the 2D mesh, Broadcast down rows, reduce across columns.
\end{enumerate}
\subsection{Sparse Partitionings}
\begin{enumerate}
    \item To use the 1D collectives, the matrix must be distributed in a row and column locality (RCL) fashion.
    \item My results explore a blocked, cyclic, and random partitioning of rows and columns.
    \item Load imbalance is important.
\end{enumerate}

\subsection{Dataflow Algorithm}
\begin{enumerate}
    \item Assuming RCL, SpMV can be broken down into our two simple 1D collectives.
    \item Algorithm proceeds in two phases. Everyone waits for all broadcasts to complete (locally) and then contributes to their reductions in order.
    \item Note that this is NOT bulk-synchronous. Reductions near the top of the grid can begin before those further down.
    \item Data indices do not need to be communicated because x values are broadcast in order and reductions are processed in order.
\end{enumerate}

\subsection{Communication}
\begin{enumerate}
    \item The 1D collectives model the communication of SpMV
    \item Whole SpMV communication can be approximated with just 1 reduction (correct P and B) and 1 broadcast. Think of this as matching the broadcast from top right down to bottom right, and then the reduction along the whole bottom row. This is the largest comm distance and the limiting factor.
    \item Vertical bcast requires small reticle adjustment because tehre are fewer reticle
\end{enumerate}

\subsection{Compute}
\begin{enumerate}
    \item record local compute time on every PE. Take the max.
    \item In practice, all compute does not happen perfectly in parallel. This is an approximate understanding of compute.
\end{enumerate}

\subsection{Matrix Layout}
\label{sec:layout}

In addition to the uniformly random matrices, we evaluate our algorithm on a selection of real world matrices from SuiteSparse.
These matrices introduce structure which produces load imbalance under the basic 2D blocked decomposition.

Important note: We are limited by the 48 KB of local memory, and after stack and other variable allocation, this correlates to a max NNZ per pe of around 8000. This is a key limiting factor determining which matrices and layouts we can evaluate. A similar constraint applys to the number of matrix rows per PE row (or the size of the vector input and output), which further restricts our testing space.
Of the 12 matrices in our random suite sparse selection, only 7 can be mapped to the hardware, and only under certain mapping schemes.
