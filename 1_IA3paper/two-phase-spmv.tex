\begin{abstract}
    Sparse matrix vector multiplication (SpMV) is a crucial component of many numerical workloads, from linear solvers to graph algorithms. SpMV is characterized by expensive, irregular memory access and computational load imbalance, making it a challenging and widely studied kernel in high-performance computing.

    We study SpMV on a novel hardware accelerator, the Cerebras Wafer-Scale Engine (WSE). The WSE integrates almost 1 million processing elements on a single silicon wafer and promises extremely low-latency, high-bandwidth memory access. Exploiting these advantages, however, requires the right algorithm and data placement, presenting a difficult design problem particularly for unstructured sparse workloads.

    We present the first algorithm for SpMV on the WSE and a companion communication model, with evaluation of both across various matrix sizes and sparsity structures. To provide context, we compare the WSE SpMV implementation to a CuSparse equivalent on the Nvidia H200 and achieve substantial speedup across both randomly generated matrices and a SuiteSparse selection. This work provides insight into the utility of dataflow architectures like the WSE for general sparse workloads and informs the most important directions for future work.
\end{abstract}

\section{Introduction}
The sparse matrix-vector product (SpMV) is among the most heavily studied kernels in high-performance computing, but nonetheless remains difficult to accelerate: its performance is governed by memory access patterns dictated by the sparsity structure of the input, which varies widely across problem domains. As a result SpMV has seen extensive study including across many different hardware platforms, from CPUs and GPUs to distributed systems and processing-in-memory (PIM) architectures \cite{gao2024systematicliteraturesurveysparse,surveyspmv}.

The sensitivity to memory access cost demonstrated in SpMV highlights a rising consideration in computing, namely the growing gap between compute throughput and memory bandwidth. This motivates architectures that depart from the
traditional model of a small number of powerful cores drawing from a shared, hierarchical
memory. Spatial dataflow architectures instead distribute memory directly on chip via a 2D
mesh of many simple processing elements (PEs), each paired with fast local memory and
connected to its four cardinal neighbors. Under this model, computation happens where data already
lives rather than requiring it to travel through a shared memory hierarchy.

In this work, we develop an algorithm for SpMV on such a spatial dataflow accelerator, the Cerebras Wafer-Scale Engine (WSE). The WSE integrates a 2D PE mesh of almost 1 million PEs onto a massive square silicon area, and has demonstrated dramatic performance gains on the machine learning workloads it was originally designed for \cite{benchmarkllms,cerebras-blog,cerebras_story}.
Recent work has also demonstrated exciting results for more general scientific workloads on the WSE, particularly for applications that map well to the WSE's spatial mesh. This includes stencil applications, molecular dynamics, finite volume computation, and fast fourier transforms \cite{wse_faststencil_rocki,wse_md,wse_mcpt,wse_stencil_jacquelin}.

The existing scientific work on the WSE focuses primarily on problems with regular, structured data access. In this work, we begin exploration into more unstructured workloads on the WSE, using SpMV as our initial case study. While SpMV can be approached from a matrix-free perspective in specific contexts and implemented using stencils, we do not make any assumptions about the matrix structure. Rather, we consider any general sparse matrix stored in COO and CSR formats.

We describe an algorithm for SpMV that can be broken down into two simple primitives on the WSE: 1D broadcast and reduce. We outline and analyze the different parameters to our algorithm and how they impact performance. Additionally, we present a corresponding communication model for SpMV. To provide deeper context for SpMV on the WSE, we present a thorough performance analysis and a comparison to an Nvidia H200 GPU.

\section{Background}
The WSE-3 is made up of around 900,000 PEs each with 48KB of local memory and a full wafer peak bandwidth of 21 PB/sec. Each PE has a router with connections to its four cardinal neighbors and a local general purpose compute engine (CE). While the maximum size of a conventional chip is limited by the size of a \textit{reticle}, the lithographic stencil used when printing circuits onto silicon, the WSE-3 enables wafer-scale fabrication by stitching reticles together to produce a chip roughly 22cm in dimension \cite{manufacturingwse,hu2023waferscalecomputingadvancementschallenges}. As discussed in Section \ref{sec:colls}, the resulting mesh achieves very low latency inter-PE communication with a slight overhead across reticle boundaries.

To program the WSE, Cerebras supports a high-level machine learning framework via the Cerebras Software Platform CSoft \cite{csoft_platform}. More general purpose computing is enabled via the low level Cerebras SDK \cite{cerebras_sdk_whitepaper}. In this work, we use a third programming framework \textit{Tungsten and Paint}. Tungsten is a not-yet public, actively evolving programming
language and compiler for the WSE, and Paint is the corresponding communication orchestration language. As with any developmental compiler, some of the implementation choices in this work (Section \ref{sec:coovscsr}) reflect current compiler behavior and may shift as the stack matures. Recent work implemented in Tungsten notes hand-tuning compiler
output to achieve the best performance
\cite{wse_md}, which we do not attempt.

\section{Related Work }
SpMV has seen extensive study spanning techniques for sparse matrix storage, mixed-precision, autotuning, and portability to different architectures. Gao et al. provide a recent and comprehensive literature review \cite{gao2024systematicliteraturesurveysparse}. The areas of SpMV development most relevant to our work are in distributed memory, and PIM architectures.

In the distributed memory context, inter-node communication becomes a dominant performance factor. Matrix partitioning strategies, including hypergraph and recursive block partitioning, are used to reduce communication \cite{hypergraphforspmv,hypergraphcatalyurek,hypergraph,recursiveblock}. Most closely related to the current work, Bylina et al. map SpMV to a 2D grid of CPUs using a 2D blocked matrix partitioning, equivalent to our 'blocked' mapping described in Section \ref{sec:mapping} \cite{2dpartitioningspmv}.

PIM architectures exhibit similar characteristics to dataflow architectures, with the goal of colocating memory and compute. Xie et al. develop SpaceA, a PIM architecture for SpMV specifically, and a mapping scheme to optimize for load balance and locality by colocating rows of the matrix with similar sparsity structure \cite{PIM-spaceA}.

Luczynski et al. originally present a set of 1D and 2D collectives implemented in CSL for the Cerebras WSE \cite{Luczynski_2024}. In this work, we focus on the 1D broadcast and reduce where each PE contributes exactly one vector element to each broadcast or reduce. These collectives are described by the first two parameters in Table \ref{tab:notation}, where $P$ denotes the number of PEs used in the collective and $B$ denotes the number of consecutive vectors that are pipelined through the collective. Note that the original presentation of this model understands $B$ differently, as the 'vector length', but both definitions refer to the same context.


Luczynski et al. develop a performance model for the 1D reduction and broadcast based on the parameters $P$ and $B$ and an additional variable $T_r$, the ramp latency. Specifically, $T_r$ captures the latency between message arrival at a PE's router to message arrival at the PE's compute engine, visualized in Figure \ref{fig:ramp-latency} for a row of three PEs, each with a local router and CE.

As highlighted in Figure \ref{fig:ramp-latency}, we update the performance model to (1) explicitly label the single-hop latency between PEs as $S$, and (2) include reticle boundary crossing latencies $T_{ret}$.
In accounting for $T_{ret}$ into our performance model, we require a third additional parameter $C$ which denotes the number of reticle boundaries crossed. In practice, $C$ depends on both the length of the PE region $P$ and if the collective is vertical (column) or horizontal (row), as the reticle size is different for each dimension (we find reticles to be approximately 64 PEs wide by 168 PEs tall).

Luczynski et al. use a ramp latency $T_{ramp}$ of 2 cycles, while an earlier work from Tramm et al. finds 7 cycles. Through empirical evaluation, we find $T_r = 5$, $S = 2$, and $T_{ret} = 9$, and these values are used throughout this work.

\subsection{Performance Model}

The performance model for both collectives can be broken into a latency term and a throughput term. The latency term describes how long it takes a single iteration of broadcast or reduce to complete, and the throughput term describes how closely multiple iterations can be pipelined.

\textbf{Broadcast} on the WSE makes use of WSE router support for simultaneously forwarding a message to the next PE while sending it down the ramp. For a single message broadcast through a chain of $P$ PEs, this means that the only observed latency is the ramp traversal at the beginning and end of the chain, along with the $P$ PE-to-PE hops. The down-ramp latencies into each PE along the chain are not included because they are overlapped with message forwarding. In terms of throughput, multiple broadcasts can be pipelined perfectly.

Luczynski et al. use the model in Equation \ref{eq:oldbcast} to describe this pattern. The throughput term $B$ aligns with our findings, but the latency term doesn't account for the 2 cycle PE-to-PE latency $S$. This marks the largest difference between our models. Our proposed update in Equation \ref{eq:newbcast} adds this $S$ dependency and additionally accounts for the reticle crossing overhead, dependent on $T_{ret}$ and $C$.

\textbf{Reduction} follows a similar logic to broadcast, but requires data to pass through the CE of each PE. This impacts the latency term, which now includes ramp latencies for each PE along the chain, instead of just the beginning and end. The Luczynski et al. model in Equation \ref{eq:oldred} captures this latency term as $(2T_r + 2)P$ and does in fact account for $S=2$, if not explicitly. We rewrite the model in terms of $S$ and include our reticle overhead term $T_{ret} C$ in Equation \ref{eq:newred}.

\begin{tcolorbox}[equationbox,title={1D Collective Model Updates}]
    \begin{align}
        M_{b}(B, P)      & = B + P +  2T_r
        \label{eq:oldbcast}                                \\
        M_{r}(B, P)      & = B + (2T_r + 2) P
        \label{eq:oldred}                                  \\
        M_{b}^*(B, P, C) & = B + S * P + 2 T_r + T_{ret} C
        \label{eq:newbcast}                                \\
        M_{r}^*(B, P, C) & = B + (2T_r + S) P +  T_{ret} C
        \label{eq:newred}
    \end{align}
\end{tcolorbox}

For this evaluation, both collectives are implemented in Tungsten and Paint and evaluated on the WSE3, and measured cycle counts are converted to runtime assuming a 1GHz clock rate. In particular, these results demonstrate that our update to the latency term for the broadcast model aligns better with true performance.

\section{Two-Phase SpMV}
We implement an algorithm to compute the sparse matrix-vector product  $Ax = y$ on the WSE using the 1D collectives as a basis.
At a high level, the algorithm involves distributing the coefficients of $A$ across a 2D grid of PEs, broadcasting values of $x$ vertically through PE columns, and reducing values of $y$ across PE rows. The algorithm makes some assumptions about the matrix layout but otherwise supports a wide parameter space across various matrix mappings, sparse storage options, and PE grid size choices. In the following discussion, we assume $A \in \mathbb{R}^{N \times N}$ and use PE grid dimensions $(P_1, P_2)$, where typically $P_1 = P_2$.

\subsection{Data Distribution}
\label{sec:mapping}

\textbf{Matrix Layout:}
To use the 1D collectives for SpMV, the matrix $A$ must be distributed on the PE grid in such a fashion that two entries $a_{i_1,j_1}$ and $a_{i_2,j_2}$ are in the same PE column if $j_1 = j_2$ and the same PE row if $i_1 = i_2$. In other words, a single row or column of $A$ must be mapped to a single row or column of the PE grid, respectively. We refer to this constraint as row and column locality (RCL).

\textbf{Matrix Mappings:}
We use the term 'mapping' to refer to how the coefficients of $A$ are placed on the PE grid, where we only consider mappings that satisfy RCL. In this work, we explore three mappings: blocked, cyclic, and random.

Our blocked mapping does a basic 2D blocked decomposition of the rows and columns of $A$. This mapping is perhaps the easiest to visualize, but often produces large load imbalance across PEs, especially when the matrix has a banded or diagonal structure.

The cyclic and random mappings attempt to address this potential load imbalance by partitioning rows and columns either randomly or cyclically via a mod function. The random mapping partitions rows and columns evenly across matrices, but under a random permutation. The cyclic mapping assigns every non-zero $a_{i,j}$ to PE $P_{(i \mod P_1),(j \mod P_2)}$. This mapping works best when PE grid is not in fact square, and the dimensions $P_1$ and $P_2$ are coprime, ensuring any cyclicity in the matrix structure is not mapped directly to the grid.

\subsection{Dataflow Algorithm}
Assuming that the matrix $A$ is distributed on the 2D mesh under a mapping that preserves row and column locality, the SpMV can be conceptually
broken down into two simple 1D collective phases:
\begin{enumerate}
    \item Broadcast values of $x$ down mesh columns in the order prescribed by the mapping.
    \item Reduce rows of partial products across mesh rows also in the order prescribed by the mapping.
\end{enumerate}

Ensuring that broadcasts and reductions proceed in a prescribed order means that indices of $x$ and row indices of the reductions do not need to be communicated --- instead, they are implied by the order of arrival.
In our implementation, the values of $x$ and the resulting values of $y$ are stored in 'moat' PEs: an extra row of PEs is set aside at the top of the
mesh onto which the initial values of $x$ are loaded. Similarly, an extra column of PEs is allocated to the left of the grid wherein the result values $y$ are stored
once computed. Alternatively, the implementation could be updated to stream the values of $x$ and $y$ on and off the mesh, eliminating the need for moat PEs and the corresponding buffers for $x$ and $y$. This streaming optimization is left for future work.

Locally, each PE processes the SpMV in three distinct phases with serialization points between them.
\begin{enumerate}
    \item Store all incoming broadcasts for the PE column
    \item Complete all local compute for each output row
    \item Contribute all results to row reductions
\end{enumerate}
In theory, local synchronizations between these three components are not necessary. For example, early incoming broadcasts could trigger some subset of the compute before all broadcasts are received.
While Tungsten does provide constructs that would support more overlap
of communication and computation here, we evaluated several different approaches and found that the serial approach consistently performed best.

Even though the kernel for each PE enforces this serialization, the global algorithm is not bulk-synchronous. Broadcasts and reductions can proceed
in increments of single PE steps, allowing incremental progress through the grid and an overlap of communication and computation. In practice, this might look like reductions near the top of the grid completing before those lower in the grid. We expect that this wavefront behavior would allow some pipelining of multiple SpMVs but this evaluation is left for future work.

\subsection{PE-Local Storage Format}
We implement two standard matrix storage formats: CSR and COO. These dictate only the storage of each PE's individual domain and are completely independent of the mapping strategies.
The COO algorithm \ref{alg:coo} avoids the nested for loop of the CSR algorithm \ref{alg:csr} and is therefore apparently friendlier to the Tungsten compiler.
On the other hand, COO replaces the $Aptr$ data structure, which has length corresponding to the number of local rows, with
a rowids data structure with an entry for each non-zero, potentially contributing to memory pressure depending on the sparsity structure of the matrix.
In evaluation in Section \ref{sec:coovscsr}, we find that COO is typically much more efficient than CSR.

\begin{algorithm}
    \caption{SpMV Kernel in CSR Format}
    \label{alg:csr}
    \begin{algorithmic}[1]
        \ForAll{$r \in \texttt{rows}$}
        \State $sum \gets 0$
        \For{$nnz \gets \texttt{Aptr}[r]$ \textbf{to} $(\texttt{Aptr}[r+1]-1)$}
        \State $sum \gets sum + \texttt{vals}[nnz] \cdot \texttt{x}[ \texttt{colids}[nnz]]$
        \EndFor
        \State $\texttt{partial}[r] \gets sum$
        \EndFor
    \end{algorithmic}
\end{algorithm}

\begin{algorithm}
    \caption{SpMV Kernel in COO Format}
    \label{alg:coo}
    \begin{algorithmic}[1]
        \ForAll{$n \in \texttt{nnzs}$}
        \State $sum \gets \texttt{vals}[nnz] \cdot \texttt{x} [\texttt{colids}[nnz]]$
        \State $r \gets \texttt{rowids}[nnz]$
        \State $\texttt{partial}[r] \gets \texttt{partial}[r] + sum$

        \EndFor
    \end{algorithmic}
\end{algorithm}

\section{Communication Model}
One benefit of designing the SpMV algorithm around 1D broadcast and reduce is that the performance model for the 1D collectives is easily extended to a communication model for SpMV. The communication patterns of SpMV map to the 1D collective models in two parts:
\begin{enumerate}
    \item $P_2$ parallel broadcast streams, one in each PE column. Each stream has pipeline depth $B_b = \frac{N}{P_2}$ and length $P_b = P_1$.
    \item $P_1$ parallel reduce streams, one in each PE row. Each stream has pipeline depth $B_r = \frac{N}{P_1}$ and length $P_r = P_2$.
\end{enumerate}

Our model makes the simplifying assumption that all broadcasts across PE columns occur perfectly in parallel, and similarly for all reduces across PE rows. We also approximate that there is a serialization point between the broadcasts and the reduces. The SpMV communication model is then simply a sum of the broadcasts and reduces, as described in Equation \ref{eq:spmvmodel}. Note that the numerators in the $C$ terms come from the observed size of the reticles in the horizontal and vertical directions respectively.
\begin{tcolorbox}[equationbox,title={SpMV Communication Model}]
    \begin{equation}
        \begin{split}
            M_{spmv} & = M_{r}^*(\frac{N}{P_1}, P_2, \lfloor{\frac{P_2}{64}}\rfloor)   \\
                     & +  M_{b}^*(\frac{N}{P_2}, P_1, \lfloor{\frac{P_1}{168}}\rfloor) \\
        \end{split}
        \label{eq:spmvmodel}
    \end{equation}
\end{tcolorbox}

In most contexts, this model will underpredict the runtime for SpMV, because it does not account for computation. This means that we expect the model to be better when the limiting compute factor (namely the max number of nnzs per PE) is smaller. In evaluation, we explicitly time the compute time on each PE and use the slowest PE to understand the overall compute time.

\section{Experimental Setup}
We evaluate our SpMV algorithm and communication model on a WSE-3 in 32-bit floating point precision assuming a 1GHz clock rate. The GPU baseline comparisons
are made with a cuSparse implementation evaluated on a single H200.
\subsection{Matrix Selection}
We evaluate on two classes of matrices: custom randomly generated matrices and a selection of matrices from SuiteSparse.
The randomly generated matrices are constructed based on matrix size and number of nonzeros, with nonzeros distributed uniformly throughout the matrix. In particular, we use a suite of randomly generated matrices, varying the number of nonzeros per row and the number of rows. We refer to this set of matrices as the RandomSuite matrices.

\subsection{WSE Pre-processing}
Once a matrix is chosen, a pre-processing step generates the corresponding input files for the WSE.
This step requires the matrix itself, the size of the PE grid, the mapping strategy (blocked, cyclic, random), and the format (COO, CSR).
The result of pre-processing is a set of binaries describing the data to be loaded on to the device.
This pre-processing step is not measured in reported runtimes.

\subsection{CuSparse Configuration}

In our GPU performance comparisons, we use a 32-bit CuSparse SpMV implementation on a single H200.
Specifically, we use the configuration CUSPARSE\_SPMV\_COO\_ALG1 which has demonstrated the best performance on SuiteSparse matrices in recent literature \cite{gao2024systematicliteraturesurveysparse}.
On our selection, this configuration achieves up to a 1.3x speedup over the default CuPy implementation. Each GPU datapoint includes 20 warmup iterations and an average timing over 50 subsequent trials.

\subsection{Grid-Size Selection}
\label{sec:optmeshsize}
The communication model becomes useful in practice if it can guide discovery of the best configuration for a given matrix.
Particularly, we are interested in how the communication model can help select the ideal PE grid size.

We evaluate the RandomSuite matrices across various PE grid sizes to identify the optimal configuration for each. Figure \ref{fig:randsuite-wse-heatmap} visualizes the results from square matrices of dimension 8192 to 2097152 with the number of nnzs per row increasing along the y axis. As matrices get bigger and denser, the optimal grid size increases.

In practice, this suggests that the communication model alone may not be a good prediction tool, unless supplemented by a corresponding computation model.

\subsection{GPU Comparison}

In this section, we evaluate the WSE SpMV algorithm against a CuSparse implementation on a single Nvidia H200.
This GPU comparison serves as a baseline and reference datapoint, not a strict comparison for the sake of demonstrating superiority of one algorithm or architecture over the other. Such a comparison would necessitate a more comprehensive analysis of power draw differences and a pass over various GPU implementations, including possibly custom kernels. We note that the fashion in which the WSE algorithm loads the full matrix into fast local memory first might be more comparable to a GPU implementation that uses entirely shared memory. A more thorough comparison accounting for these points is left for future work.

We first evaluate the GPU across our RandomSuite space varying the number of nonzeros per row and the number of rows. Figure \ref{fig:gpu-vs-wse-varydensity} shows the throughput achieved for increasing matrix size on the H200 and WSE. The heatmap in Figure \ref{fig:randomsuite-speedup} shows the speedup achieved by the WSE over the GPU for each of the RandomSuite matrices. Note that the WSE results here use the optimal configuration found in section \ref{sec:optmeshsize}. The performance trends here suggest that if the SpMV implementation could be updated to address the memory constraint limits, the speedup may continue to scale.

The scaling properties of both architectures are further investigated in Figure \ref{fig:gpu-vs-wse-varydensity}, which plots the RandomSuite results but looks at how the throughput varies with the number of rows and density of the matrices. The two platforms diverge in how throughput responds to matrix size. On the GPU, throughput for different nonzero densities converges toward a common bandwidth as $N$ grows. At small matrix sizes, the dense matrices perform substantially better, but as the matrix size grows the impact of density diminishes. The WSE shows the opposite trend: throughput continues to climb with $N$ across all densities, and denser matrices pull further ahead rather than converging. This gives some intuition for the growing speedup with matrix size observed in Figure \ref{fig:randomsuite-speedup}, particularly for dense matrices: rather than saturating a shared bandwidth ceiling, the WSE's distributed on-chip memory lets throughput scale with the size of the problem, at least up to the local memory capacity limits discussed in Section \ref{sec:optmeshsize}.

\section{Conclusion}
This work presented the first algorithm for sparse matrix-vector
multiplication on the Cerebras Wafer-Scale Engine, built on a pair of
1D collective primitives, along with a companion communication model
derived from an updated performance model for those collectives. Across
both randomly generated and SuiteSparse matrices, our implementation
achieves substantial speedup over a cuSparse baseline on an Nvidia
H200, though performance remains sensitive to load imbalance across
PEs and, for denser matrices, becomes increasingly compute-bound. These results suggest that the WSE's
on-chip mesh is a promising substrate for unstructured sparse workloads
where good data placement is achievable, but also highlight that
placement itself is the central open problem: our blocked, cyclic, and
random mappings are simple relative to the more sophisticated
partitioning strategies used in distributed and PIM contexts, and
closing that gap is a natural direction for future work.
